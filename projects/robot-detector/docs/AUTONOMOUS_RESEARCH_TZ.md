# Техническое задание: автономная научно-исследовательская разработка Market Robot Detector

**Версия:** 1.0, 21 ноября 2026 года  
**Область:** только projects/robot-detector в открытом репозитории IskanderAbdullin/Analytics  
**Постоянный контроль конечной цели:** https://github.com/IskanderAbdullin/Analytics/issues/72  
**Актуальное машинно-читаемое состояние:** research/autonomy_state.json  
**Исполнитель:** любой следующий агент, получивший доступ к репозиторию и данному ТЗ.

## 1. Конечная цель, а не очередная задача

Создать открытый, воспроизводимый исследовательский комплекс, который по анонимным биржевым событиям, публичным сделкам и синхронизированному L2 способен выявлять **наблюдаемые признаки алгоритмического исполнения**, отделять их от случайной и обычной рыночной активности, объяснять неопределённость, сравнивать научные гипотезы и проверять устойчивость результатов.

Критерий завершения проекта — **научно обоснованный, воспроизводимый результат с прозрачными ограничениями**, а не число коммитов, зелёный CI или впечатляющее значение одной метрики. Если на доступных данных проблема доказуемо неидентифицируема, допустимый конечный результат — доказанная граница идентифицируемости плюс надёжный инструмент тестирования/оценки таких гипотез, а не выдуманная точность.

Нельзя утверждать по публичной ленте физическую личность владельца заявки, число независимых роботов, достоверную рыночную FDR без ground truth, причинность или манипуляцию на основе одного L2/print признака.

## 2. Режим «длинная автономная цепочка»

**Главное правило: завершение очередного этапа НЕ является событием остановки.** Исполнитель обязан после каждого этапа сразу выбрать и начать следующий наиболее полезный незаблокированный этап в том же активном запуске.

Внутри одного запуска выполнить цикл:

1. Восстановить состояние: прочесть этот файл, проектный AGENTS.md, README, research/autonomy_state.json, открытый issue #72 и последние фактические коммиты/CI. Не принимать историю чата вместо проверяемого репозитория.
2. Зафиксировать одну конкретную проверяемую гипотезу/инженерное улучшение и его acceptance criteria. Если данные ранее просмотрены, обозначить эксперимент как retrospective; новую проверочную выборку, метрики и пороги фиксировать ДО её открытия.
3. Реализовать минимально полезное законченное изменение: код, unit/negative tests, контроль источника, документацию, ожидаемые ограничения.
4. Проверить локально или дешёвым CI доступные тесты. Если результат отрицательный, сохранить его в том же виде: не подменять выборку, фазу, порог или критерий.
5. Сделать осмысленный commit и fast-forward push в рабочую ветку; проверить SHA удалённой ветки и статус нужных тестов. Не использовать force-push.
6. Обновить checkpoint с полученным доказательством, SHA, выполненными/непройденными проверками, блокерами, новым приоритетом, точным NEXT_ACTION. Лучше включать checkpoint в коммит этапа. При необходимости отдельный короткий checkpoint-коммит.
7. **Без промежуточного ответа пользователю** сразу перейти к пункту 2 с новым этапом, пока позволяют активный запуск, доступные инструменты, безопасность и ресурсы.

Не останавливаться по причинам «прошёл один тест», «закрыл issue», «CI зелёный», «есть commit/push», «готов отчёт», «выросла точность», «найден один новый источник». Эти события только входы для решения, что исследовать дальше.

Пользователь не должен каждый раз писать «продолжай» для следующего логически очевидного этапа **в пределах одного действующего запуска**.

## 3. Сообщения, управление автономностью и реальные ограничения платформы

- Предпочтение пользователя — **никаких временных итогов между этапами**. Отвечать одним объединённым итогом по окончании доступного активного запуска или при существенном блокере; не оформлять промежуточные стадии как завершение проекта.
- Молчание не означает фоновую работу. Агент ChatGPT **не может обещать бессрочное непрерывное исполнение между запусками чата**, если не настроен реально работающий планировщик и его полномочия не проверены.
- Если контекст/инструмент/время запуска заканчиваются: выполнить безопасный checkpoint с точным NEXT_ACTION, результатами и идентификаторами и завершить этот запуск честным сообщением. При последующем запуске сразу восстановить прогресс из checkpoint и продолжить без повторного объяснения старых задач.
- При сбое инструмента использовать альтернативный доступный метод; при сбое одного источника переключиться к другому независимому научному этапу. Не просить подтверждений для очевидных технических решений, если пользователь уже разрешил соответствующие действия.
- Нельзя менять правила безопасности, скрытно подключать компьютер либо притворяться, что всё проверено, если исходное выполнение не удалось.
- Работу с локальным Windows PC Agent и компьютерной автоматизацией производить **только при явном разрешении пользователя** и лишь когда она действительно полезна. На дату создания ТЗ проект успешно обрабатывался на GitHub, локальное копирование не требовалось.
- GitHub Actions разрешены только в открытых репозиториях; в приватных их не запускать. Дорогие эксперименты — разовые/ручные, дешёвые offline unit tests — автоматически. Не создавать бесконечные Actions workflow.
- Никогда не выводить пароли/секреты и не отправлять реальные торговые заявки. Источники — research-only, наблюдение/read-only, корректная атрибуция и разграничение прав на сырой архив и авторский научный код.

## 4. Система решений: что делать дальше

После этапа составить как минимум три кандидатных продолжения (можно мысленно/в checkpoint), оценить:

- **Научная ценность:** устранение угрозы валидности, независимый negative control, новый L2 источник, честное сравнение гипотез.
- **Воспроизводимость:** проверяемые исходные данные, версии, исходный код, deterministic seeds, независимый CI.
- **Информационная ценность отрицательного результата:** опровержение гипотезы часто важнее повышения видимой метрики.
- **Зависимости/блокеры:** нет ли существенной недоступности сырой L2, согласования или предрегистрации.
- **Цена/ресурсы/риск:** отдавать приоритет коротким высоким по пользе проверкам. Не занимать локальный диск сырой историей без необходимости.

Приоритет по умолчанию: исправление ошибки научной достоверности > строгая независимая проверка > важнейший новый источник L2 > базовая инженерия > новый эвристический детектор > косметика.

**Запрещено подгонять значимость, выбирая после просмотра выгодную дату, инструмент, фазу, seed, интервалы, threshold или набор отрицательных примеров.**

## 5. Последовательность стратегических эпиков (можно переставлять по ожидаемой пользе)

### A. Контроль данных и корректная семантика (обязательный фундамент)

- Единый typed schema: source_id, exchange/event/receive time, timezone, quote depth/coverage, message type, resting side vs aggressor, source digest/provenance, gaps, snapshot-after-event vs before-event.
- Согласованные и сбалансированные входные публичные prints и L2 snapshots; отсутствие утечки приватных synthetic agent IDs в публичные признаки.
- Безопасный исторический replay, нагрузочные synthetic tests, обработка некорректных, дублированных или пропущенных событий, честный отчёт о покрытии.
- Исторический демо LOBSTER AMZN 2012-06-21: уже проверены 269 748 пар message/book с 10 уровнями. Следующий этап — исследовательские инструменты для **сравнения гипотез на этих публичных демонстрационных данных**, без загрузки оригинальных CSV в GitHub. Дополнительные коммерческие архивы не считать доступными.

### B. Ясные научные гипотезы и baselines

- Простейший baseline, случайная модель с учётом активности и формы стакана, nulls по времени и объёму.
- Candidate features: регулярность агрессивных исполнений, разметка кластеров одинакового timestamp, плотность и продолжительность активности, orderflow imbalance, изменение mid/spread/queue/доступной глубины, устойчивость ритма к смещению time bins.
- Исключить механические эффекты: 1-print bin всегда односторонний; split fills одного рыночного ордера не являются несколькими независимыми роботами; особенности пассивной стороны message.
- Сравнить с консервативными event/cluster preserving controls, а не только с наивной перестановкой BUY/SELL.

### C. Ground truth в контролируемых сценариях

- Synthetic market backgrounds и целевые агенты, чтобы **иметь известную истинную метку только для оценки**.
- Обособленная стадия извлечения публичных признаков, до которой oracle agent identity недоступен.
- Holdout сценарии, seeds, regimes и instrument-like параметризации, не виденные при подборе порогов.
- Evaluations: false alarms, precision/recall, coverage, calibration и stability лишь там, где у данных действительно есть oracle labels.
- Negative-control тест без целевого алгоритма столь же обязателен, как positive-control с ним.

### D. Реальные неразмеченные рынки

- Пререгистрированные даты и инструменты, источники и лицензионные границы; раздельные интервалы разработки и untouched проверки.
- Cross-market transfer с сохранением **всех отрицательных исходов**. Опыт LTCUSDT/BCHUSDT за 17–20 ноября: сильная неоднородность; BCH преимущественно не превосходил 8 control shuffles. Это не универсальный бинарный detector.
- Разделение цельных source days и зависимых фаз 0/10/20s; 8 shuffle replicates не дают статистически надёжной рыночной FDR.
- Реальные источники не дают физические owner labels; не смешивать descriptive event statistics с подтверждением робота.

### E. Сборка результата и выпуск

- Открытая воспроизводимая research CLI, replay/feature extraction/null evaluation, документация запусков, отчёт из одной команды.
- Автоматические unit, integration, adversarial source tests, безопасные CI триггеры, низкий расход GitHub Actions.
- Методологический отчёт: проверенные гипотезы, опровергнутые гипотезы, ограничения, точные данные/seed/время, материал воспроизведения, единый JSON отчёт.
- Read-only streaming/optional OsEngine adapter — только если реально помогает исследованию и офлайн pipeline корректен.

## 6. Критерии готовности одного этапа (DoD)

Этап считается завершённым только когда:
- есть конкретный проверяемый результат (файлы/код/данные/доказательство), не только план;
- записаны входные зависимости, источник, действительная область данных и ограничения использования;
- выполнены или явно помечены недоступными relevant tests; известна причина каждого отказа;
- при исследовательских сравнениях есть negative cases и сохранена предрегистрация;
- результаты, включая fail/negative, не скрыты и не переписаны;
- commit + подтверждённый push без force, remote SHA и CI evidence зафиксированы;
- NEXT_ACTION и связанный с конечной целью reason уже выбраны.

Затем НЕ отвечать отдельным «готово», а начать следующий этап.

## 7. Критерии готовности всего проекта (Release gate)

Закрывать issue #72 и считать конечную цель выполненной только при независимой проверке:
1. Повторяемость всех ключевых результатов с чистого checkout, без секретов, закрытых/неразрешённых архивов или скрытых файлов.
2. Нормализация message/print/L2, сильные negative tests и проверяемое покрытие источников.
3. Честная оценка синтетической точности только на независимом oracle-labelled holdout; отдельно — описательная реальная валидация без claims о владельцах.
4. Воспроизводимая отчётность по устойчивости к фазе, активности, split fills, неполноте данных и выбору инструмента/дня.
5. Сравнение с базовыми моделями и указание причин, когда сложный алгоритм не даёт преимущества.
6. Указаны все отрицательные гипотезы и границы применения, не утверждается недоказанная идентификация роботов.
7. Удобная CLI/публикация собственных исходников и методов, минимум расходов CI, понятная лицензия собственного кода и отдельная атрибуция исходного датасета.

Если объективно невозможен пункт из-за недоступных реальных source labels или рыночного L2, указать как явную недоказанность и предложить доказуемый ограниченный научный результат. Нельзя снижать требования задним числом для объявления победы.

## 8. Протокол checkpoint и возобновления

Единственный машинно-читаемый рабочий checkpoint: research/autonomy_state.json.

Держать в нём:
- статус проекта, конечную цель и master_issue;
- базовый последний подтверждённый commit и ссылки на evidence;
- completed stages с настоящими результатами, не просто галочками;
- активный/следующий stage ID, ожидаемые файлы, критерии приёмки, реальные блокеры;
- очередь следующих осмысленных задач и их научные приоритеты;
- runtime ограничения и безопасную процедуру resume.

Перед окончанием активного сеанса **всегда оставлять точную инструкцию возобновления**, чтобы следующий агент открыл репозиторий и выбрал следующий этап без просьбы заново объяснять содержание исследования. Если checkpoint конфликтует с GitHub HEAD, обнаружить конфликт и обновить на основании фактической истории, а не переписывать чужую работу.

State файл — часть исходников проекта, не имитация работающего демона. Обновлять его после завершённой работы (или безопасного recovery), избегать секретов и больших артефактов. Собственная задача без изменения state не должна оставаться «потерянной» после push.

## 9. Следующее действие на момент создания ТЗ

**RD-L2-RESEARCH-01:** продолжить именно исследовательскую часть по публичному демо LOBSTER AMZN, опираясь на проверенный paired message/orderbook парсер. Реализовать безопасный event-time feature/replay pipeline с раздельной pre-event/post-event семантикой, агрегатами стакана и синтетическими tests/negative controls. Не выгружать строки исходного ZIP в открытый репозиторий. Отдельно от реального L2 и synthetic oracle сравнить, какие признаки можно наблюдать, а какие неидентифицируемы.

После RD-L2-RESEARCH-01 автоматически выбрать RD-L2-RESEARCH-02 по новой информации, а не останавливаться из-за успешной проверки первой фичи.

**Нормативная формулировка:** «Работай над конечной научной целью, не над очередной галочкой. Каждый успешный stage служит входом следующего stage; коммит/CI/отчёт не являются причиной остановки. Продолжай в рамках активного исполнения, а при вынужденной остановке оставь проверяемый checkpoint, который делает последующее продолжение непосредственным».
