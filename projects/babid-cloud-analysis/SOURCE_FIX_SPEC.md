## 2. Факты, не равные доказанному RCA

**SRC-01 (подтверждённое устройство API):** `IBroker.RequestPosition()` возвращает `void`, а `BrokerPositionEvent` содержит лишь `Lots`. `TInvestBroker.RequestPosition` выполняет `GetPositionsAsync` в `Task.Run`, не добавляя сквозного ID к ответу. `Engine.Risk` хранит общие `_positionRequestedUtc` и `_positionRequestQuiet`. Поэтому текущий контракт не даёт движку связать каждую позицию с конкретным запросом или надёжно отбросить запоздавший результат. **Не доказано**, что такие ответы столкнулись в реальном инциденте.

**SRC-02 (подтверждённая ветвь кода):** `SynthesizeMissingTrades` добавляет SYNTHETIC исполнение по цене ордера либо рыночной отметке. `AddFills` при `HasSynthetic(order)` может игнорировать позднюю настоящую сделку, если её добавление превысило `FilledByState`; эта ветвь не меняет синтетическую цену и booked P&L. **Не доказано**, что эта ситуация произошла в реальной истории, но её нужно покрыть тестами.

**SRC-03 (подтверждённая логика защиты):** `OnBrokerPosition` сравнивает `brokerLots - Journal.NetLots` с сохранённой внешней базой и при двух расхождениях может вызвать `Halted`, в том числе если разница возвратилась к нулю. Код объясняет возможную повторную остановку, **но не происхождение первых двух лотов**.

**SRC-04 (существующие защитные механизмы):** `OnOrderReport` сохраняет заказ под контролем, если поздний RPC отказ противоречит уже принятому stream-событию; `BeginResync` устанавливает `_synced=false` до проверки активных ордеров. Не удалять эти механизмы при исправлениях.


## 2.1. Проверка контрактов T-Invest GetPositions — отрицательный результат для простой гипотезы

По официальной документации [T-Bank OperationsService](https://developer.tbank.ru/invest/services/operations/methods), в `PositionsFutures` и `PositionsSecurities` поле `balance` означает **незаблокированный** баланс, а `blocked` — количество, заблокированное выставленными заявками. Поэтому само по себе суммирование `balance + blocked` в `TInvestBroker.RequestPosition` **не является свидетельством двойного счёта** и не должно заменяться на одно `balance` без отдельной проверки. Это проверка **семантики полей API**, не доказательство правильности всего метода.

Нужно дополнительно проверить для конкретной версии инструмента знак позиции, размер лота, InstrumentUid/PositionUid, доступность балансов во время клиринга и поведение при задержанных ответах; без независимого broker report исходное расхождение в 2 лота остаётся необъяснённым. Добавить тест T15: при 7 незаблокированных и 3 заблокированных единицах общая позиция должна соответствовать брокерскому определению total=10 единиц (условно; лоты пересчитать по подтверждённому инструменту), а не превращаться в ложные +7 или +13.

## 3. P0-S1 — последовательность и корреляция брокерских позиций

Файлы: `Core/BrokerEvents.cs`, `Broker/TInvest/TInvestBroker.cs`, `Trading/Engine.Risk.cs`, тестовый брокер.

1. В контракт запроса/ответа добавить монотонный `RequestSequence`, `RequestedUtc`, `CompletedUtc`, scope account/instrument, ревизию журнала и признак, был ли запрос действительно отправлен. Обеспечить связь sequence с единственным ответом либо явным отказом.
2. Разрешить не более одного in-flight position-запроса либо сохранять множество активных и принимать только подтверждённый более новый результат. При порядке завершения 11→10 ответ 10 **не** изменяет baseline, mismatch streak, risk или recovery.
3. Отдельно отслеживать неизвестную свежесть *брокерского* snapshot: новый HTTP/gRPC ответ не гарантирует актуальность самой позиции. При неопределённости повторять сверку без открытия заявок.
4. Изменившиеся fills, заявки, ревизия журнала и неquiet-окно инвалидируют снимок, относящийся к старому состоянию. Пропуск запроса по rate limit не считается подтверждением.
5. Внутри движка использовать строгую последовательность/монотонную привязку, не порядок логов с одинаковой миллисекундой. Не смешивать UTC, МСК и биржевое время.

## 4. P0-S2 — FSM согласования позиции (fail-closed)

Файлы: `Engine.Risk.cs`, `Engine.Quoting.cs`, `Engine.Orders.cs`, `RiskManager.cs`, `Journal.cs`.

- При необъяснённом изменении перейти в `ReconciliationPending`; **запретить новые открывающие заявки**, но оставить разрешённые безопасные отмены и строго ограниченные защитные действия.
- Убедиться в законченности всех partial fills, replace/cancel и статусов; провести проверку как известных, так и неизвестных активных ордеров.
- После стабилизации собрать минимум два независимых свежих position-снимка с разными RequestSequence. Нельзя считать двукратное повторение одного ответа независимыми проверками.
- Раздельно хранить `Journal.NetLots`, исходную подтверждённую external baseline, необъяснённые лоты, время и доказательство последней успешной сверки.
- Возвращение расхождения к 0 не должно автоматически удалять доказательства, маскировать внешнюю сделку или сбрасывать `Halted`. После независимой проверки и явного разрешённого reset не допускать циклических ложных остановок из-за устаревшего baseline.
- Запретить автоматическое приведение позиции рынка/журнала к совпадению. При недоказанном результате оставаться в pending/halted.

## 5. P0-S3 — reconciliation SYNTHETIC → настоящий fill

Файлы: `Engine.Orders.cs`, `Journal.cs`, `Accounting/PnlTracker.cs`, WAL/ledger, mock broker.

- SYNTHETIC — **предварительная**, не подтверждённая биржей запись с источником, объёмом и расчётной ценой.
- При поздней подлинной сделке сопоставлять её с одним или несколькими provisional fills данного ордера, поддерживать частичные количества, не удваивать лоты.
- Дедупликация подтверждённых сделок по корректному scope account/instrument/order/trade_id с сохранением при restart и stream replay; fallback без trade_id допускается только с явной неопределённостью.
- Корректировать цену, комиссию и реализованный учёт **компенсирующим событием или воспроизводимым replay**, не переписывая незаметно историю. При отсутствии брокерских сумм показывать provisional P&L, а не independently reconciled.
- Конфликт `FilledByState`, подтверждённых fills и остатка provisional переводит робот в сверку и запрещает открывающие заявки.

## 11. Готовое средство для проверки бухгалтерской коррекции

В публичном `Analytics` модуль `analysis/audit_history.py` расширен: теперь распознаёт запись `Income accounting position (...) differs from the journal (...)` и формирует при офлайн-запуске `history/accounting_alignments.csv`. Отчёт содержит только время, каталог логов, номера исходных строк и числовые `pnl_net_before`, `journal_net`, `delta_lots`, без trade IDs и без претензии на брокерскую верификацию. Модуль считает все найденные события и явно фиксирует усечение после 2000 строк.

Проверяемое предсказание для одной из возможных причин скачка +2: между двумя строками `fills.csv`, если разрыв вызван `CheckInternalConsistency`, должен существовать локальный accounting notice с `delta_lots=+2` и временнóй совместимостью. При предположении отсутствия других учётных событий возможный пример — `pnl_net_before=34`, `journal_net=36`, затем покупка 5 с результатом net 41. **Это только условное предсказание, а не установленный факт.** Если запись отсутствует при полной доказанной целостности логов — эту конкретную версию надо ослабить, не подгонять результат.

Обновление публичного анализатора НЕ означает обновления имеющейся Windows-копии скрипта; прежде чем использовать отчёт, необходимо удостовериться в версии анализатора и неизменности копии торговых данных. Без отдельного локального выполнения и независимой брокерской сверки первопричина остаётся unresolved.

## 12. P0-S6 — позднее исполнение отменённой/архивированной заявки

**Факт (E-033):** реальный локальный лог фиксирует Cancel/0 и примерно через 38 секунд Sell 2 по той же открывающей заявке. Лог обработанного Sell2 оставил Journal.NetLots=+36, тогда как Pnl учёл продажу и через две секунды был согласован с Journal на +2.

**Уязвимый кодовый путь (E-034):** Housekeeping вызывает Journal.Prune с grace=5s. PruneOrders может удалить Cancel/0 из коллекции позиции, сохранив объект в _byRequestId. Поздний OnOrderReport/AddFills/BookFill затем обновляет Pnl и CSV, но без Journal.Restore(order); Journal.NetLots может не отражать поздний Sell2. Удаление конкретной заявки напрямую не логируется.

**Альтернативная причина (E-035):** Order.Filled=max(FilledByState,FilledByFills). Если FilledByState уже включил Sell2, поздний trade может изменить Pnl без изменения Journal и без Prune. Требуется установить промежуточные состояния, а не выбирать объяснение по совпадающей величине +2.

### Требования к безопасному исправлению (код исходного робота не менять без отдельного разрешения)

1. Не архивировать Cancel/0 по одному истечению 5 секунд без доказанной полноты брокерских исполнений. Хранить tombstone или восстанавливаемый индекс позиции для поздних trades.
2. Любой поздний fill должен атомарно и идемпотентно отражаться как в журнале позиции, так и в Pnl. При сомнительном FilledByState или устаревшем состоянии — блокировка новых открытий до сверки, не автоматическая коррекция при отсутствии биржевой операции.

## 13. Уточнение по видимости статусов (E-039)

`OnOrderReport` может увеличить `FilledByState` при неизменном `OrderState`. Обычное сообщение о переходе состояния в этом случае не печатается; поэтому отсутствие отдельного логового события с ненулевым `filled` не доказывает, что статус не предучёл исполнение. Исторические H-006 (Prune) и H-007 (precredited status) требуют **другого наблюдаемого признака**, а не только последующего отсутствия изменения `Journal.NetLots`.

Тест T17 обязательно должен покрывать архивированную Cancel/0 с сохранённым request-id lookup и поздним трейдом **без** terminal→live перехода: восстановление связанной позиции и однократное отражение real fill в обоих учётах. T18: `OrderState=Cancel`, тихое изменение `FilledByState=0→2` и позднее получение двух лотов; дедупликация не должна добавлять позицию второй раз, но обязана сохранить экономический fill. T19: подтверждать fresh request/response position, устранять race с live activity, не принимать одинаковую величину −2 за причинное доказательство.

Отдельный контроль: в `CheckInternalConsistency` `TradesSynchronized(_journal.TrackedOrders())` не охватывает архивированные по `_byRequestId` объекты, и поэтому не может служить гарантией полноты всех трейдов. Future design: ledger completeness из durable order index, отдельный статус reconciliation-pending для завершённых ордеров, fail-closed вместо молчаливого `Pnl ← Journal`. Все изменения основного бота вне scope, только спецификация.

Локальный диагностический скрипт в этом сеансе не выполнился (`PC_AGENT_HTTP_404`), а текущий путь источников указывает на рабочий каталог: прежде любого воспроизведения необходим frozen archive + SHA-256 manifest. Это не установленная историческая первопричина.

## 11. P0-S6 — независимые часы и очередность поздней доставки (22.11, E-040)

В приватном инциденте метка исполнения из `fills.csv` на 5.026 секунды **раньше** сообщения `Cancel/0`, но робот обработал исполнение через 38.285 секунды **после** этого сообщения. Источник метки: `ReportedFill.TimeUtc` из `OrderTrade.DateTime` (stream) либо `OrderStage.ExecutionTime` (query), затем `Fill.TimeUtc` и преобразование UTC→МСК в ledger. Значит, термин «поздний fill» здесь должен относиться к получению/обработке сведений, **не обязательно** к времени совершения сделки. Сама метка времени, её синхронизация и консистентность статуса брокера без независимого источника не подтверждены.

Для будущего исправления строго разнести `SourceExecutionUtc` (как сообщил брокер), `BrokerReportReceivedUtc`, `EngineAppliedUtc`, `OrderStateObservedUtc`, `JournalArchivedUtc` и `SnapshotVersion`. Идентификатор корреляции сообщения и независимая история брокерского исполнения нужны для выводов о порядке. `Cancel/0` с более поздним локальным временем **не** означает, что брокер не исполнил объём ранее. Архивировать терминальный нулевой остаток без подтверждённой полноты истории сделок нельзя считать безопасным для учёта; изменение LIVE-кода в этом проекте запрещено.

**T20 (future mock-broker, synthetic):** вымышленная заявка получает trade execution timestamp T0, ответ Cancel/0 наблюдается T0+5 s, сообщение с этой сделкой приходит T0+43 s; наблюдаемые и source timestamps хранятся отдельно, поздняя доставка не превращается в «execution after Cancel». При наличии неразрешённого FilledByState/архивирования система должна сохранять возможность сверки, не удваивать/не терять исполнение и оставаться fail-closed до независимого подтверждения. Отдельно проверить поток status update с тем же OrderState и ростом FilledByState: отсутствие логовой строки смены State не равно отсутствию обновления. Тест не доказывает факты о реальном заказе.

## 12. Ограниченный forensic freeze (E-041)

Перед воспроизведением A-001 применять `analysis/freeze_evidence.py` лишь для локального копирования конкретных input (21.11 NVDA log, fills.csv, journal.json, journal.wal, risk.json) с контрольными SHA-256 до/во время/после копии. `reports/private` — отдельный локальный приватный каталог, не source root. Утилита не является атомарным snapshot across files, не подтверждает брокерские исполнения/полноту и не разрешает работать с LIVE торговыми процессами. **T21 (синтетический):** копирование вымышленных файлов с SHA256; изменения источника в момент копирования, symlink, traversal, duplicate destination и отсутствующие входы должны приводить к запрету/удалению неполной копии. Эти тесты проверяют инструментарий, а не первопричину реального инцидента.

## 13. P0-S7 — условный предикат Prune и альтернатива precredit (E-043)

Статически установлено: `Order.Filled=max(FilledByState,FilledByFills)`, `FillsSynchronized = FilledByFills>=FilledByState`, а `PruneOrders` удаляет лишь terminal zero-filled Settled (grace=5s, no NeedsCheck/ResyncNeeded/QueryInFlight). Silent FilledByState>0 до Prune делает удаление невозможным для данного состояния. Реальные `UpdatedUtc`/флаги/ArchivedUtc не наблюдались.

## 14. P0-S8 — независимые оси часов в аналитическом инцидентном отчёте (E-044)

Старый `position_forensics.py` создавал `incident_evidence.csv`, сортируя вместе broker-reported timestamp из fills.csv и локальную метку сообщения логгера. Это не причинная хронология: ledger содержит trade event time, а лог — receipt/processing observation time. Анализатор теперь маркирует clock_domain, source_sequence и группирует output в source-native order; сводка содержит явный `not_inferred` для междоменных причинных связей. Старые приватные отчёты повторно применять для RCA только после пересчёта, не переставляя физические строки fills.csv по времени исполнения.

## 15. P0-S9 — независимые брокерские источники и время сделки (E-045)

По официальной документации OrderTrade.date_time (и OrderStage.execution_time) — UTC-время совершения сделки, а OrderTrades.created_at — время создания сообщения; не использовать их как взаимозаменяемые с локальным received time. `GetOrderState` может не возвращать записи старше одного дня. Историческая сверка: авторизованный broker report или GetOperationsByCursor с полной пагинацией и caveats о задержанных операциях, меняющихся operation IDs и отличающихся trade_id namespaces. Не делать вызовы broker API без отдельного разрешения. Подробности в BROKER_RECONCILIATION_SPEC.md. Синтетический future T24 — abstain при неоднозначной привязке.

## 16. P0-S10 — запаздывающий fill на границе окна (E-047)

`position_forensics.py` до этой правки выбирал ledger fill по брокерскому execution-time *внутри* пользовательского локального observation window, что могло скрыть позднюю доставку исполнения, совершённого раньше начала окна. Новое opt-in `--fill-execution-lookback-sec N` (0 ≤ N ≤ 86400; default 0) допускает раннюю исходную execution запись, явно маркирует `execution_lookback=True`, выводит счётчик; время доставки из этого факта НЕ следует. Вывод по-прежнему сгруппирован по clock-domain и source row; междоменные причинные утверждения запрещены.

**T25 synthetic:** execution row на 30 s раньше начала окна, наблюдение fill на 10 s после начала. При lookback 0 ledger row не включён, log включён; при 60s ledger включён и помечен prior-execution; отрицательный lookback отклонён. Реального NVDA анализа пока нет.
