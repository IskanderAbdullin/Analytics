# Babid Cloud — независимый офлайн-анализ торговли

Это **отдельный исследовательский проект внутри Analytics**, а не модификация торгового робота.
Исходная программа и её журналы служат **входными данными только для чтения**. Здесь находятся
только аналитические Python-скрипты, тесты с вымышленными данными, документация и CI.

## Назначение

- Обнаружение дублирующихся каталогов состояния и журналов в копиях конфигурации.
- Поиск ошибок работы робота: остановки Risk/Halted, дублирующие и пропущенные исполнения,
  отклонения заявок, реконнекты и расхождения позиций брокера и журнала.
- Сверка `fills.csv` с `journal.json` с точными десятичными вычислениями.
- Оценка P&L по дням с отделением realized от mark-to-market и предупреждением о комиссиях.
- Анализ рыночных записей `.tsv`/`.tsv.gz` и проверка доступности котировок в стакане.
- Описательное сравнение параметров на разных днях, с последним днём вне обучающей выборки.

**Ограничение:** доступность котировки не равна вероятности исполнения и не является
прогнозом прибыли. Реальные комиссии, funding и проскальзывание нельзя восстановить
только из внутренних журналов робота. Бэктест исполнения через движок ещё не реализован.

## Где работать

Все разработки и GitHub Actions **только в `IskanderAbdullin/Analytics`**,
в каталоге `projects/babid-cloud-analysis`.
Внешние репозитории и работающая программа не изменяются.
В GitHub не загружаются реальные журналы, брокерские токены, конфигурации,
снимки состояния и отчёты с торговыми идентификаторами.

## Проверки (стандартная библиотека Python 3.11+)

```bash
cd projects/babid-cloud-analysis/analysis
python -m compileall -q .
python -m unittest discover -p "test_*.py" -v
```

GitHub Actions выполняют только эти проверки на Ubuntu и Windows, без секретов
и без обращения к каким-либо другим репозиториям.

## Анализ истории на локальной копии

Внешнюю папку с копией робота передавай как `--root`. Результат сохраняется
в новом, ранее не существовавшем подкаталоге `<КОПИЯ>/reports/`.
Скрипты не умеют отправлять брокерские заявки, изменять конфигурацию или
вмешиваться в запущенный процесс.

```bash
python run_offline_audit.py --root "<PATH_TO_COPIED_BABID_CLOUD>"
```

Для быстрого прогона без записей рынка:

```bash
python run_offline_audit.py --root "<PATH_TO_COPIED_BABID_CLOUD>" --skip-market
```

Полные журналы могут занимать сотни мегабайт; скрипты читают их потоково.
В результатах проверяется неизменность источников, но это **не** эквивалент
атомарного снимка файловой системы.

## О статусе

Исходные аналитические утилиты перенесены в отдельный проект и теперь имеют
собственное синтетическое CI. Реальные журналы и сделки пользователя в
публичном репозитории отсутствуют. Исходную причину расхождения NVDA на 2 лота
нельзя доказать без локальной обработки полной истории и сверки с брокером.

## Полная проверка связки анализаторов

Кроме отдельных тестов доступен `analysis/test_integration_pipeline.py`, который
создаёт исключительно **синтетический архив** конфигурации, журнала,
исполнений, P&L и сжатой записи рынка, затем пропускает его через весь
`run_offline_audit.py`. Проверяется согласованность всех отчётов,
отсутствие записи в исходные файлы и запрет повторного использования
каталога результатов. Никаких реальных торговых данных в CI нет.

## Качество и полнота биржевой записи

Дополнительная команда:

```bash
python tape_integrity.py --root "<PATH_TO_COPIED_BABID_CLOUD>"
```

Потоковый парсер точно следует `MarketRecording.cs` версии `855745b...`:
`B recvMs exchangeMs bids asks`, `T/G recvMs tradeMs ...`, `D/U` — разрывы
канала; метка `I` хранит инструмент. В журнал выводятся количество
повреждённых и пересечённых стаканов, задержка `recvMs-exchangeMs`,
обратные временные метки, восстановленные сделки, известная длительность
разрывов потока и незавершённые разрывы.

Важно: робот не записывает **неизменившийся** стакан, поэтому большой
промежуток между строками `B` сам по себе **не доказывает** потерю данных.
Вычисляемая разность временных меток не является чистой сетевой задержкой.
Скрипт не выполняет сделок, не меняет состояние робота и не называет
«лучшую» настройку без верифицированного исполнения.


## Offline markout после исполнения

Модуль analysis/execution_markout.py вычисляет для каждого исполнения из
fills.csv наблюдаемую среднюю цену стакана через 5 и 30 секунд. Пример:

    python execution_markout.py --root "<PATH_TO_COPIED_BABID_CLOUD>" --state state-nvda-iis-live --instrument NVDAperpA --day 2026-11-21

Время сделки в fills.csv — МСК (время сделки брокера). Стакан имеет время
получения UTC Unix ms. Используются только стаканы, полученные строго ДО
момента измерения; запрещены look-ahead, устаревшие снимки и переходы через
разрывы потока. По умолчанию максимальный возраст снимка 2000 мс.

Положительный markout означает сдвиг цены в выгодную сторону относительно
сделки; отрицательный — в невыгодную. Это НЕ реализованная прибыль, не прогноз,
не оценка комиссии, финансового тика или вероятности исполнения. Исследователь
явно указывает state/instrument/day, так как окончательный JSON-конфиг не
доказывает историческую принадлежность всех исполнений. Отчёты с trade_id
хранятся только локально и не публикуются.


## Временная доля подходящего стакана

Модуль analysis/time_weighted_books.py оценивает не частоту подходящих
строк стакана, а долю *времени* с известным, достаточно свежим стаканом.
На каждое состояние вводится верхняя граница возраста: 2000 мс по умолчанию.

    python time_weighted_books.py --root "<COPY>" --max-book-age-ms 2000 --levels 3,5,10,20,120

Отчёты включают covered_ms / observed_ms и buy/sell_geometry_ms.
После потери связи D/U и после устаревания снимка время считается
НЕПОКРЫТЫМ. Записи T/G могут уточнять наблюдаемый временной интервал,
но не создают новый снимок стакана. Стадия интегрирована в общий
run_offline_audit.py и не требует брокера. Это не backtest и не сигнал
для изменения реальных настроек.


## Временная история настроек (не конечный JSON)

Модуль analysis/config_epochs.py извлекает из журналов события
Engine started, Risk, Config applied, Schedule и изменения режима вручную.
Для каждого события фиксирует время МСК, распознанные параметры,
идентификатор настроек и уровень полноты сведений.

    python config_epochs.py --root "<COPY>"

Config applied содержит описание стратегии, риска и комиссий, но не все
настройки связи. Schedule меняет лишь часть параметров; старые параметры
могут наследоваться, но не все явно подтверждены. До первого события
история неизвестна, а конфиг в момент завершения работы не позволяет
восстановить предыдущие значения. Распределение торгового P&L по
полученным интервалам допускается только после независимой проверки
соответствия логов, счёта и инструмента.


## Результат сделок при наблюдавшихся настройках

Модуль analysis/fills_by_epoch.py сопоставляет реальные строки fills.csv
с интервалами Config applied / Schedule / Engine started / P&L at stop.
Связь конкретного каталога состояний и логов задаётся явно:

    python fills_by_epoch.py --root "<COPY>" --state state-nvda-iis-live --logs logs-nvda-iis-live

Результат: booked_fills_by_epoch.csv с количеством исполнений, лотами,
реализованным результатом и оценочной комиссией в каждой эпохе;
UNKNOWN — до первого подтверждённого события, после остановки,
на времени смены параметров или после последнего наблюдаемого лога.

Это распределение РЕАЛИЗОВАННЫХ результатов по моменту исполнения,
но не доходность торговой стратегии: заявку могли создать при другом
наборе параметров, открытая позиция не оценена, комиссии и funding
могут быть неполными. **Автоматическое изменение LIVE параметров запрещено.**


## Контроль качества общего отчёта

После анализа создаётся quality_gate.json с тремя возможными статусами:
locally_consistent, review_required, incomplete.

Если журналы менялись во время чтения или любой обязательный аналитический
модуль завершился ошибкой, результат получает incomplete; командная строка
возвращает код 2, сохраняя частичный отчёт. Расхождения local fills vs.
journal, неизвестные настройки и повреждённые стаканы требуют проверки.

Даже locally_consistent НЕ доказывает правильность брокерского учёта и НЕ
разрешает автоматическое изменение реальных торговых параметров.


## Общий запуск с явно подтверждаемой привязкой данных

Обычный аудит не угадывает, какой из конфигов, логов и записей рынка
соответствует конкретному роботу. Только по явным аргументам можно
добавить отчёт о результатах при изменении настроек и markout:

    python run_offline_audit.py --root "<COPY>" --epoch-state state-nvda-iis-live --epoch-logs logs-nvda-iis-live --markout-state state-nvda-iis-live --markout-instrument NVDAperpA --markout-day 2026-11-21

Все три параметра markout и оба параметра эпохи должны передаваться
вместе. При ошибке любой дополнительной стадии отчёт сохраняется,
но quality_gate.json помечает исследование неполным. Само соответствие
папок и инструмента остаётся неподтверждённым историческими конфигами.


## Хронология расхождений брокера и журнала

Модуль analysis/position_evidence.py сопоставляет подтверждённые строки
«position outside the robot changed...» с брокерской позицией, состоянием
журнала и изменением лотов между двумя проверками по fills.csv.

    python position_evidence.py --root "<COPY>" --state state-nvda-iis-live --logs logs-nvda-iis-live

Ключевой отчёт position_deltas.csv содержит четыре величины:
изменение позиции брокера, изменение журнала, изменение внешней
разницы и нетто лоты локальных исполнений между проверками.
Для расследования сохраняется небольшой список trade_id (только в
локальном отчёте). Равенство сумм НЕ доказывает, что брокер отдавал
свежие данные, а несовпадение не доказывает ручную сделку. Часы
исполнений и логов могут относиться к разным этапам доставки.

Этот модуль также запускается общим анализатором, если исследователь
явно указал --epoch-state и --epoch-logs. Без подтверждённой связи
каталогов выводы об источнике расхождения не делаются.

## Исторический охват и разбор отдельных инцидентов

`run_offline_audit.py` теперь по умолчанию ищет события **за всю доступную историю**,
а не только в фиксированные 30 минут 21 ноября 2026 года.
Узкий временной интервал можно запросить парой `--focus-start`/`--focus-end`
(время МСК, ISO); отсутствие обоих параметров означает всю историю.

Отдельный подробный отчёт по происшествию выполняется **только по явному выбору**
`--incident-state`, `--incident-logs`, `--incident-start`,
`--incident-end`; эти аргументы должны быть указаны все вместе. Например:

```bash
python run_offline_audit.py --root "<COPY>" --incident-state state-nvda-iis-live --incident-logs logs-nvda-iis-live --incident-start "2026-11-21 14:40:00" --incident-end "2026-11-21 15:10:00"
```

Не предполагается, что папка с NVDA существует или что указанные даты соответствуют реальным файлам.
Даже полное сканирование журналов ограничивает извлекаемую ленту инцидентов (не весь журнал
копируется в отчёт); сводная статистика ошибок считает все записи.

## Полнота ленты происшествий

Исторический аудит подсчитывает **все** совпавшие события, даже если
`incident_timeline.csv` хранит только первые 25 000 строк. В `summary.json`
отдельно указаны `incident_events_total`, `incident_events_omitted`,
`incident_timeline_truncated` и выбранный `incident_limit`.
Ограничение можно изменить флагом `--incident-limit` (от 1 до 1 000 000).
При усечении ленты общий quality gate выдаёт `review_required`;
успешный процесс не означает полную хронологию происшествий.

## Неполные строки журнала исполнений

`reconcile_fills.py` теперь **не пропускает молча** оборванные строки
`fills.csv`: они записываются как `truncated_row` в `anomalies.csv`,
считаются в `truncated_rows` и переводят статус соответствующего
состояния в `incomplete`. Даже если все остальные строки сходятся с
`journal.json`, нельзя объявлять источник полным. Это особенно важно
при копировании файлов во время работы робота.

## Дневной P&L и числовая полнота

При расчёте `fills_daily.csv` суммы `realized` и `fee_estimate`
накапливаются через `Decimal` без ошибок округления `float`.
Если есть дубликаты исполнений, неверные объёмы или отсутствует денежное
поле, соответствующий денежный итог остаётся **пустым (unknown)**,
а не заменяется нулём. Поля `invalid_rows`, `missing_realized`,
`missing_fees` и `duplicate_trade_ids` позволяют увидеть причину.
Это бухгалтерские значения внутреннего журнала, не банковская
сверка и не полноценный результат с учётом funding.

## Точность и неполные данные графика результата

`pnl_daily.csv` теперь использует `Decimal` для денежных значений
и просадок (`max_drawdown`), а целочисленные миллисекунды — для времён.
Если известна дата, но значение P&L повреждено, или временные метки
идут назад, результат за день получает `quality=unverified`;
`change` и `max_drawdown` остаются пустыми. Колонки
`invalid_samples` и `out_of_order_samples` показывают причину.
График P&L робота — **не** независимая оценка стоимости брокерского
счёта: funding, открытые позиции и внешние сделки требуют отдельной сверки.
